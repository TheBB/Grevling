# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Grevling (Norwegian for "badger") is a CLI tool for running **parameter studies**. Given a set
of parameters and their possible values, it runs a sequence of shell commands once per parameter
combination, each in an isolated working directory built from templated input files, then captures
the outputs (files, regex matches from stdout, walltimes) into a per-case SQLite database plus
per-run log directories on disk. It is meant to replace ad-hoc bash scripts for this workflow.

A **case** is a directory containing a config file plus its input files. Config is written in the
[Gold language](https://thebb.github.io/Gold) (`grevling.gold`); YAML (`grevling.yaml`,
`badger.yaml`) is legacy and only loaded when the file is explicitly named `.yaml`/`.yml`. Both
`grevling` and `badger` are installed as console entry points for `grevling.__main__:main`.

Captured data lives in the storage dir (default `.grevlingdata/`). The **SQLite database
(`grevling.db`) is the source of truth**; alongside it are the per-instance log directories (raw
stdout/stderr and captured files). `dataframe.parquet` is an incidental export produced by
`grevling collect` / `dump` — a convenience view, not the primary store. The whole directory is
safe to delete and is regenerated by `grevling run`.

Direction of travel: the DB currently stores each instance's captured values as a single JSON blob
column (`db.Instance.captured`). This is being progressively "deconstructed" into real typed
columns, and downstream consumers (plotting, analysis) should read from the DB rather than the
dataframe over time.

## Development commands

Uses [uv](https://docs.astral.sh/uv/) for dependency and environment management. Tooling is
`ruff` (lint + format), `pyrefly` (type checking), `pytest`.

- `make sync` — `uv sync` (creates `.venv`, installs deps + the `dev` dependency group)
- `make test` — the full CI gate: `pytest` + `pyrefly` + `lint-check`
- `make pytest` — `uv run pytest`
- `make pyrefly` — `uv run pyrefly check` (config in `[tool.pyrefly]`, `legacy` preset)
- `make lint` — `uv run ruff check --fix`
- `make format` — `uv run ruff format`
- `make lint-check` — `ruff check` + `ruff format --check` (no writes; what CI runs)
- `make build` — `uv build`

Run a single test: `uv run pytest tests/test_run.py::test_echo`, or select by expression with
`uv run pytest -k echo`. Note most run/parse tests are parametrized over both `.yaml` and `.gold`
config and over API vs CLI invocation (see `tests/common.py`), so one logical test is several
cases.

CI (`.github/workflows/python-package.yml`) runs `make test` on Python 3.12–3.14 across Linux,
Windows and macOS.

Supported Python and core-dependency (numpy, pandas) versions follow
[SPEC 0](https://scientific-python.org/specs/spec-0000/): Python is supported for 3 years after
release, core packages for 2. `requires-python` and the numpy/pandas lower bounds in
`pyproject.toml` encode this, so PEP 604 (`X | Y`) unions and PEP 695 (`def f[T]`) generics are
used throughout — do not reintroduce `typing.Optional` / `typing.Union` in annotations.

## Architecture

The flow from config file to stored results passes through these layers:

### 1. Config loading and refinement (`grevling/schema/`)

`schema/__init__.py::load()` reads a Gold or YAML file into a Python object, then validates it in
two stages:

- **`raw.py`** — permissive pydantic models. Many fields accept unions (a capture may be a string,
  a dict, or a list) and Gold callables (since Gold config can contain functions). Mirrors what a
  human writes.
- **`refined.py`** — rigid lowest-common-denominator models. `raw.CaseSchema.refine()` converts
  everything to canonical form; anything that must be evaluated per-instance (scripts, `evaluate`
  expressions, `where` conditions, file maps, `logdir`) becomes a `Callable[[api.Context], ...]`.

The rest of the codebase only ever sees `refined` models. `grevling/grevling.gold` is a Gold
standard library (`cmd`, `copy`, `glob`, `linspace`, `gradspace`, `plot`, `loglog`, …) that user
configs pull in via `import "grevling"`; `libfinder()` in `schema/__init__.py` resolves that
import.

### 2. `Case` (`grevling/__init__.py`)

The central object, used as a context manager. On `__enter__` it acquires an inter-process lock
(`fasteners`), opens the SQLite DB via SQLAlchemy, and runs `auto_migrate()`. Holds the
`ContextProvider`, the pre/post `FileMapTemplate`s, the `ScriptTemplate`, the `TypeManager`, plots
and plugins. Methods `run` / `capture` / `collect` / `plot` correspond to CLI subcommands.

### 3. Parameter space and context (`parameters.py`, `context.py`)

`ParameterSpace` is the cartesian product of the parameters. For each combination `ContextProvider`
merges constants, evaluates the `evaluate` block and the `where` filter, and yields a `Context`
(a `dict` subclass, `api.Context`). Keys prefixed `g_` are Grevling builtins (`g_index`,
`g_logdir`, `g_sourcedir`, `g_started`, `g_finished`, `g_success`, `g_walltime_*`).

### 4. `Instance` (`grevling/__init__.py`) and the DB (`db.py`)

An `Instance` is one parameter combination, backed by a `db.Instance` row (index, logdir, context
JSON, captured JSON, status). Status lifecycle:
`Created → Prepared → Started → Finished → Downloaded`. The `db` module (SQLAlchemy models) and
this table are the persistent state Grevling operates on; `captured` is a JSON column today but is
where the normalization work (real columns per captured value) is headed.

### 5. Workflow / pipeline (`workflow/__init__.py`, `workflow/local.py`)

`Pipeline` is an asyncio queue-based fan-out pipeline of `PipeSegment`s. `LocalWorkflow.pipeline()`
wires `PrepareInstance → RunInstance → DownloadResults`. The `-j` CLI flag sets the number of
concurrent copies of the run segment. Workflows are a pluggable subclass registry keyed by a
`name` attribute (`Workflow.get_workflow`); only `local` is implemented (`--azure` is referenced
but absent).

### 6. Workspaces (`api.py` ABCs, `workflow/local.py` impls)

`Workspace` / `WorkspaceCollection` abstract a directory. Each instance runs in a fresh temporary
workspace (`WRK`). **Prepare** copies source → `WRK` through the pre `FileMap`, rendering Mako
templates on the way. **Run** executes the script in `WRK`. **Download** copies `WRK` → the log
dir (`LOG`, under the storage dir) plus its `.grevling/` bookkeeping subdir, runs captures, then
destroys the temp workspace.

### 7. Templating (`render.py`)

Mako. `render()` handles template files, command arguments, filenames and `logdir`. Passing
`mode="shell"` adds a `shlex.quote` filter for safe interpolation into shell strings. `sin`/`cos`
(numpy), `rnd`, `sci` are exposed to templates.

### 8. Script execution (`script.py`)

`Command` runs via `asyncio.subprocess`. A string command runs through the shell; a list command
runs exec-style. Optional `container` runs it inside `docker run`. Each command writes
`<name>.stdout`, `<name>.stderr`, and appends `key=value` bookkeeping lines to `grevling.txt`
(walltimes, `g_started`, `g_finished`, `g_success`).

### 9. Capture and typing (`capture.py`, `typing.py`)

`Capture` compiles a regex (or a "simple" integer/float-with-prefix pattern) and extracts named
groups from stdout, with mode `first` / `last` / `all`. `CaptureCollection` (another `Context`
subclass) accumulates values, coercing each through the `TypeManager`. `GType` is a small type
lattice (`Integer`, `Floating`, `String`, `Boolean`, `Datetime`, `List`, `AnyType`) with
`merge` / `coerce` / pandas-dtype; `TypeManager` maps capture names to `GType` and predefines the
`g_*` builtins.

### 10. Collect and plot (`__init__.py`, `plotting.py`)

`Case.collect()` reads the Downloaded instances and writes `dataframe.parquet` (pyarrow) indexed
by `g_index` — a derived export for external consumption, kept working but not the primary path.
`plotting.py` currently still consumes that dataframe; the intended direction is for it (and any
other analysis) to query `grevling.db` directly. It has a backend subclass registry (`matplotlib`,
`plotly`, `csv`) selected by available optional dependencies; parameter plot modes are
fixed / variate / category / ignore / mean.

### 11. Migrations (`grevling/migrations/`, `db.py`)

Alembic revisions (`v0`, `v1`, `v2`) plus a custom "major version" layer: `DB_MAJOR_VERSION` and
the `MIGRATORS` dict in `__init__.py` upgrade pre-SQLite data directories (old `state.json` +
`.grevling/*.txt` files) into the current schema. The root `alembic.ini` is for authoring
revisions; at runtime the config in `grevling/migrations/` is used. `tests/test_migrate.py`
exercises the upgrade path against fixture data.

### 12. Plugins (`api.Plugin`)

A plugin is any importable module exposing a `Plugin` class. It is instantiated at `Case` init and
may contribute Click subcommands surfaced under `grevling plugin <name>`.

## Conventions

- Every module starts with `from __future__ import annotations` (ruff enforces this).
- ruff: line length 110, broad ruleset — prefer `pathlib` over `os.path`, put type-only imports
  under `TYPE_CHECKING`, follow the import-convention / return / simplify rules it checks.
- Type checking is `pyrefly` with the `legacy` preset (mypy-like strictness). Third-party stubs
  live in `stubs/` (`search-path`); `goldpy` is a stubless compiled extension and is mapped to
  `Any` via `replace-imports-with-any`.
- Pydantic `BaseModel` subclasses are runtime-evaluated, so their fields may reference names not
  imported under `TYPE_CHECKING`.
- Version is set in both `pyproject.toml` and `grevling/__init__.py`; `bumpversion` config keeps
  them in sync.
- Test fixture cases live under `tests/data/`, grouped by scenario, usually with parallel `.gold`
  and `.yaml` variants.
